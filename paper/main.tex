\begin{abstract}
Exact hierarchical agglomerative clustering (HAC) of large spatial datasets is limited in practice by the \(\Onotation{n^2}\) time and memory required for the full pairwise distance matrix. We present \emph{GSHAC} (Geographically Sparse Hierarchical Agglomerative Clustering), a system that makes exact HAC for geographic data feasible at scales of millions of features on a commodity workstation. We replace the distance matrix with a sparse geographic distance graph containing only pairs within a user-specified geodesic bound~\(\hmax\). The graph is constructed in \(\Onotation{n \cdot k}\) time via spatial indexing (KD-tree or Ball-tree), where~\(k\) is the mean number of neighbors within~\(\hmax\), and its connected components define independent subproblems for standard HAC. We prove that the resulting cluster assignments are \emph{exact}---identical to those from a dense matrix---at any cut height \(h \le \hmax\) for linkage criteria whose inter-cluster dissimilarity is bounded below by the closest inter-point distance, namely single, complete, and average linkage. For single linkage, an MST-based path avoids dense sub-matrices entirely, keeping memory in \(\Onotation{n_k + m_k}\) per component regardless of component size. When the local density is bounded---the typical case for geographic data---the mean neighborhood size~\(k\) stays small as~\(n\) grows and both time and memory scale near-linearly. On a 2-million-point sample of GeoNames (global named places), GSHAC clusters at thresholds of 1, 5, 10, and 20\,km---each in under 2.5\,minutes on a single 30\,GiB workstation, with whole-pipeline peak memory ranging from 0.5 to 22\,GiB across thresholds---whereas the dense distance matrix (\(\approx\!29\,\text{TiB}\)) is orders of magnitude beyond available memory. To our knowledge, these are the largest demonstrations of exact HAC on geographic data on a single workstation, opening the door for applied researchers and practitioners to analyze geographic data with millions of features using substantially reduced resources. We provide an implementation compatible with Python's scikit-learn that enables direct integration into GIS workflows.
\end{abstract}

Hierarchical Agglomerative Clustering (HAC) is a fundamental unsupervised learning technique widely used across numerous scientific disciplines because it provides an informative, multi-scale representation of data structure without requiring a predefined number of clusters \cite{mullner2013fastcluster}. In spatial analysis and geo-data science, HAC is highly valued for exploratory data analysis, geochemical anomaly detection, and discovering nested regional structures \cite{sadeghi2025clustering}. Unlike partitional methods such as K-Means, which require the number of clusters to be specified in advance and assume spherical cluster shapes, HAC provides a rich, multi-resolution dendrogram that can be cut at arbitrary levels \cite{sadeghi2025clustering}.

Despite its analytical utility, standard HAC suffers from severe scalability bottlenecks. Constructing the hierarchical dendrogram traditionally requires calculating and storing a full pairwise distance matrix, which imposes an \(\mathcal{O}(n^2)\) memory footprint and an \(\mathcal{O}(n^3)\) or \(\mathcal{O}(n^2log~n)\) time complexity \cite{nguyen2014sparsehc, gagolewski2016genie}. This quadratic wall renders exact HAC computationally infeasible for large modern datasets on commodity hardware \cite{hendrix2013scalable}.

To overcome these limitations and allow scalable applications, a variety of approaches have been proposed across different fields. Methods such as BIRCH and CURE utilize data summarization (e.g., CF-trees) or random sampling with multiple representatives to approximate the hierarchy in a single or a few passes \cite{zhang1996birch, guha1998cure}. For single-linkage clustering, distributed and parallel computing architectures, such as MapReduce and Message Passing Interface (MPI), have been leveraged to partition the Minimum Spanning Tree (MST) computation across multiple nodes \cite{jin2015incremental, hendrix2013scalable}. In general metric spaces, algorithms have incorporated Approximate Nearest Neighbor (ANN) data structures and Locality Sensitive Hashing (LSH) to achieve subquadratic runtimes by trading exactness for speed \cite{moseley2020hierarchical}. Additionally, memory-efficient online algorithms like SparseHC process distance matrices in a chunk-by-chunk manner, exploiting sparsity to reduce memory consumption for biological data \cite{nguyen2014sparsehc} but require a pre-computed sparse matrix.

For geographic data specifically, variants of HAC have been effectively applied, such as the spatial-constraints Ward-like algorithm proposed in \cite{chavent2018clustgeo}. Furthermore, Maus (2026) recently proposed a graph-indexing method to compute sparse pairwise distances for HAC suitable for large spatial datasets \cite{maus2026data}. By applying a maximum spatial distance threshold, the method partitions geographic features into independent groups that can be computed efficiently with low memory requirements \cite{maus2026data}. However, this work has a strict application focus on mining land use and does not provide formal mathematical proofs that the approach generalizes across different standard linkage methods, nor does it prove that it strictly reduces computing time and memory bounds.

In this paper, we present GSHAC (Geographically Sparse Hierarchical Agglomerative Clustering), a system that makes exact HAC for multiple linkage methods feasible for millions of geographic features on commodity hardware. The system leverages the First Law of Geography (``Everything is related to everything else, but near things are more related than distant things''~\cite{tobler1970computer}), which implies that, in spatial and geographic contexts, features separated by vast geographic distances are highly unlikely to merge until the very final stages of 
the hierarchical tree. Therefore, rather than computing a dense distance matrix, GSHAC leverages spatial indexing (e.g., KD-trees~\cite{bentley1975quad} and Ball Trees~\cite{omohundro1989balltree}) to construct a sparse 
geographic distance graph in $\mathcal{O}(n(\log n + k))$ time, where $k$ is the mean number of neighbors within a user-specified geodesic threshold $h_{\max}$. In practice, when the sparsity assumption holds, that is, when $k \gg \log n$, this reduces to $\mathcal{O}(n \cdot k)$, which remains linear in $n$ for fixed $k$. We formally prove that the connected components of this sparse graph constitute independent subproblems, guaranteeing that the resulting cluster assignments are strictly exact for single, complete, and average linkage at any cut height $h \leq h_{\max}$. We make the following contributions:

\begin{enumerate}

  \item A system design that combines spatial indexing, connected-component decomposition, and MST-based single-linkage into a practical pipeline for exact HAC on geographical data at scale. We prove that this approach is exact for single, complete, and average linkage---linkage criteria whose inter-cluster dissimilarity is bounded below by the closest inter-point distance---at any cut height \(h \le \hmax\); Ward linkage is exact in practice for spatially compact clusters but is not guaranteed in general.

  \item Empirical evaluation on a synthetic fixed-domain benchmark (\(n\) up to \(50{,}000\)), two standard 2-D clustering benchmarks (two moons and two circles) used to illustrate exactness, and a 2-million-point sample of location names from GeoNames (\(n = 2{,}000{,}000\)) \cite{geonames2025}, with baselines including \texttt{fastcluster}, PySAL, scikit-learn, and HDBSCAN.

  \item An open-source Python implementation with a scikit-learn-compatible \texttt{SparseAgglomerativeClustering} estimator \url{https://github.com/mine-the-gap/gshac}.

\end{enumerate}

\section{Related work}

The related literature is organized into six thematic areas, covering exact and approximate hierarchical methods, sparse and scalable clustering, density-based approaches, and spatial clustering tools.

\textbf{Exact HAC and Classical Bottlenecks} 

Standard implementations of HAC, such as the widely used \texttt{fastcluster} package for R and Python \cite{mullner2013fastcluster}, provide highly optimized routines for standard linkage criteria (e.g., single, complete, average, Ward). However, these exact algorithms are still fundamentally limited by $\mathcal{O}(n^2)$ memory requirements when processing dense dissimilarity matrices \cite{mullner2013fastcluster}. In geo-data science, frameworks such as ClustGeo \cite{chavent2018clustgeo} incorporate spatial constraints by combining a feature distance matrix with a geographic distance matrix using a mixing parameter. While effective for identifying spatially contiguous clusters, these methods retain the $\mathcal{O}(n^2)$ cost of dense matrix operations, limiting their applicability to smaller regional datasets \cite{chavent2018clustgeo}.

\textbf{Single Linkage and Minimum Spanning Trees}

The mathematical equivalence between single-linkage clustering and the Minimum Spanning Tree (MST) has long been established \cite{gower1969minimum}. Algorithms such as SLINK compute the single-linkage hierarchy in optimal $\mathcal{O}(n^2)$ time and $\mathcal{O}(n)$ space \cite{sibson1973slink}. Recent advances have introduced fast parallel algorithms for Euclidean MSTs (EMST) using Well-Separated Pair Decompositions and KD-trees \cite{wang2021fast}. While these parallel methods can cluster tens of millions of points efficiently, they generally require distributed systems or massive multi-core hardware instances with hundreds of gigabytes of RAM \cite{wang2021fast}. 

\textbf{Sparse and Cutoff-Based Clustering}

To mitigate memory issues, algorithms like SparseHC \cite{nguyen2014sparsehc} process distance matrices chunk-by-chunk using a predefined distance cutoff, ensuring exact dendrograms up to that threshold \cite{nguyen2014sparsehc}. However, SparseHC requires the input data to be pre-sorted and is restricted to specific linkage types (single, complete, average) \cite{nguyen2014sparsehc}. 

\textbf{Scalable and Approximate Hierarchical Clustering}

When exactness is relaxed, several highly scalable hierarchical algorithms exist. The Sub-Cluster Component (SCC) algorithm \cite{monath2021scalable} and the Tree Grafting (Grinch) method \cite{monath2019scalable} build hierarchies over billions of points. Grinch uses local rotations and global graft operations to dynamically restructure the tree, whereas SCC uses independent sub-cluster merging \cite{monath2021scalable}. However, these algorithms generally produce non-binary trees or heuristic structures that do not perfectly approximate exact HAC unless highly restrictive mathematical conditions are met \cite{monath2021scalable}. Similarly, the Genie algorithm \cite{gagolewski2016genie} adjusts the standard linkage criteria using a Gini-index to prevent the chaining effect and resist outliers, but it alters the classical HAC definitions and can still incur long computation times on standard machines compared to simple geometric bounds \cite{gagolewski2016genie}.

\textbf{Density-Based Spatial Clustering}

In geographic domains, algorithms like HDBSCAN \cite{mcinnes2017hdbscan} and OPTICS \cite{ankerst1999optics} natively exploit spatial sparsity and density to group points efficiently. While these density-based methods are highly effective for spatial anomaly detection and noise handling, they solve a fundamentally different objective than classical HAC \cite{ankerst1999optics}.

\textbf{Spatial Clustering Tools}

A recent review~\cite{sadeghi2025clustering} identifies hierarchical approaches as important for scale-sensitive spatial analysis, yet current tools remain limited by the \(\Onotation{n^2}\) bottleneck. scikit-learn's \texttt{Agglomerative\-Clustering}, for instance, supports a sparse \texttt{connectivity} parameter \cite{pedregosa2011sklearn} that constrains which pairs may merge, but it still computes pairwise distances internally and does not provide the component-wise decomposition needed for scalable distance-threshold HAC at large~\(n\).

\texttt{libpysal.weights.DistanceBand} from PySAL \cite{rey2007pysal} constructs sparse spatial weight matrices from distance thresholds using KD-trees, but stores binary or inverse-distance weights rather than actual geographic distances, and provides no exact HAC implementation. ClustGeo \cite{chavent2018clustgeo} extends Ward clustering with spatial constraints but requires the full \(\Onotation{n^2}\) distance matrix and has been demonstrated only for \(n \lesssim 10^3\).

A complementary line of recent work in ACM TSAS targets scalability for spatial clustering through different mechanisms than ours. PAGE~\cite{alrashid2023page} parallelises spatially-constrained regionalization for large polygon datasets via heuristic search subject to user-defined region constraints; its output is a single non-hierarchical partition optimised under a maximum-region constraint, whereas GSHAC produces an exact dendrogram cuttable at any height \(h \le \hmax\). HierGP~\cite{oje2025hiergp} achieves scale through hierarchical grid partitioning with user-controlled accuracy bounds, trading data fidelity for analytical throughput; GSHAC takes the opposite trade-off, processing every original feature without aggregation while exploiting geographic sparsity in the distance graph. Bicriteria Shapes~\cite{rottmann2025bicriteria} produces a hierarchically nested sequence of polygon aggregations parameterised by a perimeter--area bicriteria optimisation solved via graph cuts; like GSHAC it serves multi-scale-of-detail analyses, but optimises a different objective (shape compactness vs.\ distance threshold) and operates on polygon geometries rather than on a generic distance graph.

\section{Theoretical formulation}
\label{sec:theoretical}

\subsection{Problem}
\label{sec:problem}

Let \(\mathcal{X} = \{x_1, \ldots, x_n\}\) be a set of~\(n\) spatial features with pairwise distance function~\(d: \mathcal{X} \times \mathcal{X} \to \mathbb{R}_{\ge 0}\) (geodesic or projected Euclidean). Let \(\hmax \in \mathbb{R}_{>0}\) be a user-specified maximum clustering distance, and \(H = \{h_1, \ldots, h_T\}\) with \(h_t \le \hmax\) be the
cut heights at which cluster assignments are required.

\begin{definition}[Geographic distance graph]
Let $\mathcal{X} = \{x_1, \ldots, x_n\}$ be a set of $n$ spatial features and $\hmax \in \mathbb{R}_{>0}$ a user-specified distance threshold. The geographic distance graph at radius $\hmax$ is the weighted undirected graph $G_{\hmax} = (\mathcal{X}, E, w)$, where:
\begin{itemize}
    \item $\mathcal{X}$ is the set of nodes, one per spatial feature; \item $E = \{(i,j) : i \neq j,\; d(x_i, x_j) \le \hmax\}$ is the set of edges, connecting every pair of features whose geodesic distance does 
    not exceed $\hmax$; and \item $w : E \to \mathbb{R}_{>0}$, defined by $w(i,j) = d(x_i, x_j)$, 
    is the edge weight function, assigning to each edge its exact pairwise distance.
\end{itemize}
Pairs $(i,j)$ with $d(x_i, x_j) > \hmax$ are absent from $E$ and contribute no entry to the distance graph, yielding the sparsity exploited by GSHAC.
\end{definition}

\begin{definition}[Connected component]
A connected component of~\(G_{\hmax}\) is a maximal set of features \(\mathcal{C} \subseteq \mathcal{X}\) such that every pair in~\(\mathcal{C}\) is connected by a path of edges in~\(E\).
\end{definition}

The goal is to compute, for each \(h \in H\), the same cluster assignment that would result from running HAC on the full dense distance matrix~\(D\), while computing and storing only the entries of~\(D\) corresponding to edges in \(G_{\hmax}\).

\subsection{Algorithm}
\label{sec:algorithm}

Algorithm~\ref{alg:main} groups the work into two phases. \emph{Phase~1} builds the sparse geographic distance graph: (i)~spatial index construction, (ii)~candidate pair discovery via range queries and exact distance computation, and (iii)~connected-component decomposition. \emph{Phase~2} runs HAC independently within each component, with a fast MST path for single linkage that avoids materialising any dense sub-matrix. The key departure from the dense baseline is that only \(|E| = \Onotation{n \cdot k}\) distances are computed and stored, where \(k = |E| / n\) is the mean node degree in~\(G_{\hmax}\).

\begin{algorithm}[!h]
\caption{GSHAC: exact HAC via a sparse geographic distance graph}
\label{alg:main}
\begin{algorithmic}[1]
  \Require Point coordinates $\mathcal{X} = \{x_1,\ldots,x_n\}$;
    distance bound $\hmax$;
    linkage method $L \in \{\text{single, complete, average, Ward}\}$;
    cut heights $H \subseteq (0, \hmax]$
  \Ensure Cluster-label vector $\mathbf{c}^{(h)} \in \mathbb{Z}^n$ for each $h \in H$

  \Statex \textbf{Phase 1: Build sparse geographic distance graph}
  \State Build spatial index $\mathcal{T}$ over $\mathcal{X}$
    \Comment{Euclidean or haversine}
  \State $\mathbf{S} \leftarrow$ empty $n \times n$ sparse symmetric matrix
  \For{$i = 1$ \textbf{to} $n$}
    \State $N_i \leftarrow \mathcal{T}.\textsc{RangeQuery}(x_i, \hmax)$
    \For{$j \in N_i$ \textbf{with} $j > i$}
      \Comment{upper triangle}
      \State $s_{ij} \leftarrow d(x_i, x_j)$
      \State $\mathbf{S}[i,j] \leftarrow \mathbf{S}[j,i] \leftarrow s_{ij}$
    \EndFor
  \EndFor
  \State $\{\mathcal{C}_1,\ldots,\mathcal{C}_K\} \leftarrow \textsc{ConnectedComponents}(\mathbf{S})$

  \Statex \textbf{Phase 2: Component-wise HAC}
  \State Initialise $\mathbf{c}^{(h)} \in \mathbb{Z}^n$ to $\mathbf{0}$ for each $h \in H$
  \State $g \leftarrow 0$
    \Comment{global cluster-ID offset}
  \For{$k = 1$ \textbf{to} $K$}
    \If{$|\mathcal{C}_k| = 1$}
      \Comment{singleton: no merges to compute}
      \State $g \leftarrow g + 1$
      \For{$h \in H$}
        \State $\mathbf{c}^{(h)}[\mathcal{C}_k] \leftarrow g$
      \EndFor
      \State \textbf{continue}
    \EndIf
    \State $\mathbf{S}_k \leftarrow$ sparse sub-matrix of $\mathbf{S}$ restricted to $\mathcal{C}_k$
    \If{$L = \textbf{single}$}
      \Comment{MST fast path: no dense sub-matrix}
      \State $\mathcal{M}_k \leftarrow \textsc{MinimumSpanningTree}(\mathbf{S}_k)$
      \State $Z_k \leftarrow \textsc{LinkageFromMST}(\mathcal{M}_k)$
        \Comment{union-find - edges}
    \Else
      \Comment{dense path for complete / average / Ward}
      \State $\mathbf{D}_k \leftarrow \bigl[d(x_i, x_j)\bigr]_{i,j \in \mathcal{C}_k}$ recomputed from coordinates
        \Comment{includes pairs $> \hmax$}
      \State $Z_k \leftarrow \textsc{Linkage}(\mathbf{D}_k,\, L)$
    \EndIf
    \State $m_k \leftarrow 0$
    \For{$h \in H$}
      \State $\boldsymbol{\lambda}_h \leftarrow \textsc{CutTree}(Z_k, h)$
        \Comment{local labels in $\{1,\ldots,n_h^{(k)}\}$}
      \State $\mathbf{c}^{(h)}[\mathcal{C}_k] \leftarrow g + \boldsymbol{\lambda}_h$
      \State $m_k \leftarrow \max(m_k,\, \max \boldsymbol{\lambda}_h)$
    \EndFor
    \State $g \leftarrow g + m_k$
  \EndFor
  \State \textbf{return} $\{\mathbf{c}^{(h)}\}_{h \in H}$
\end{algorithmic}
\end{algorithm}



\subsection{Correctness}
\label{sec:correctness}

\paragraph{Intuition.}
The proof rests on a single observation: no merge at height \(h \le \hmax\) can involve features from different connected components, because all cross-component pairs have distance \(> \hmax\) by definition. This holds whenever the linkage's inter-cluster dissimilarity is bounded below by the closest inter-point distance, which covers the most common criteria:
\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=1pt]

  \item \emph{Single linkage}: the merge height equals the minimum inter-cluster distance; all cross-component minima exceed \(\hmax\).

  \item \emph{Complete linkage}: the merge height equals the maximum inter-cluster distance, at least as large as the minimum.

  \item \emph{Average linkage}: the merge height is the mean over all cross-cluster pairs, which exceeds \(\hmax\) when every pair does.

\end{itemize}
Ward linkage is an exception: its merge criterion is the increase in within-cluster variance, proportional to the distance between cluster \emph{centroids} (scaled by cluster sizes), which is \emph{not} bounded below by the minimum inter-point distance. We treat this case separately after the theorem.

\begin{theorem}[Exact equivalence]
\label{thm:exact}
Let $\ell$ be a linkage method whose inter-cluster dissimilarity is bounded below by the minimum inter-point distance, $D_\ell(\mathcal{A}, \mathcal{B}) \ge \min_{i \in \mathcal{A},\, j \in \mathcal{B}} d(x_i, x_j)$---which holds for single, complete, and average linkage---and assume all pairwise distances in $\mathcal{X}$ are distinct. For any cut height $h \le \hmax$, the cluster assignment produced by Algorithm~\ref{alg:main} is identical (up to label permutation within each component) to the assignment produced by HAC on the full dense distance matrix~$D$.
\end{theorem}

\begin{proof}
We show that no merge required to produce the cut at height $h \le \hmax$ involves a pair $(x_i, x_j)$ with $d(x_i, x_j) > \hmax$.

\noindent\emph{Intra-component merges.} All edges within a connected component $\mathcal{C}_k$ have weight $\le \hmax$ by definition. The dense sub-matrix $\mathbf{D}_k$ contains all pairwise distances within $\mathcal{C}_k$. HAC applied to $\mathbf{D}_k$ produces the same dendrogram as HAC applied to the rows/columns of~$D$ restricted to $\mathcal{C}_k$, since no cross-component entry is involved.

\noindent\emph{Inter-component merges.} Let $\mathcal{C}_k$ and $\mathcal{C}_l$ be two distinct components. Because they are disconnected in~$G_{\hmax}$, every pair $(x_i \in \mathcal{C}_k,\; x_j \in \mathcal{C}_l)$ satisfies $d(x_i, x_j) > \hmax$. By the hypothesis on $\ell$, the merge height obeys $D_\ell(\mathcal{C}_k, \mathcal{C}_l) \ge \min_{i \in \mathcal{C}_k, j \in \mathcal{C}_l} d(x_i, x_j) > \hmax$ --- for single linkage it equals this minimum, and for complete and average linkage it is at least as large. The inter-component merge therefore occurs at height $> \hmax$ and is absent from any cut at $h \le \hmax$.

\end{proof}

\paragraph{Tied distances.} The distinctness assumption rules out exactly tied dissimilarities, under which the complete- and average-linkage dendrogram is not unique and \emph{any} exact algorithm is defined only up to tie-breaking; ties are measure-zero for continuous coordinates. Single linkage requires no such assumption: the partition at any cut \(h \le \hmax\) is uniquely determined by the set of pairwise distances not exceeding~\(h\), regardless of the order in which tied merges are traversed (see Section~\ref{sec:results}).

\begin{corollary}
The sparse matrix $\mathbf{S}$ contains all information needed to produce exact HAC dendrograms at every cut height $h \le \hmax$ for single, complete, and average linkage.
\end{corollary}

\paragraph{Ward linkage.} Ward's merge criterion is the increase in within-cluster sum of squares, proportional to the distance between cluster centroids (scaled by cluster sizes), and is \emph{not} bounded below by the minimum inter-point distance. A component that spatially surrounds another---for example, a ring of points whose nearest-neighbor spacing is \(\le \hmax\) but whose radius exceeds \(\hmax\), enclosing a central point farther than \(\hmax\) from every ring point---can have nearly coincident centroids even though all cross-component pairs exceed \(\hmax\). Dense Ward may then merge the two below \(\hmax\), which the component decomposition cannot reproduce, so Theorem~\ref{thm:exact} does not extend to Ward in general. For the spatially compact clusters typical of geographic data this configuration does not arise: GSHAC recomputes each component's full sub-matrix from coordinates, so Ward is exact \emph{within} every component, and it reproduces the dense Ward partition in all of our experiments (Section~\ref{sec:results}).

The HAC step within component~\(k\) costs \(\Onotation{c_k^2 \log c_k}\) with priority-queue-based implementations, or \(\Onotation{c_k^2}\) with \texttt{fastcluster}~\cite{mullner2013fastcluster}. \paragraph{Practical regime.}
For geographically clustered data, the common case for natural and anthropogenic features, components are small (\(c_k \ll n\)) and numerous. In this regime, \(\sum_k c_k^2 \ll n^2\) and the system is substantially faster than the dense baseline. The worst case is \(K = 1\) (all features in one component), which reduces to the dense baseline. The speedup in distance computations and storage is exactly \(n^2 / (2m)\), which grows linearly with \(n / k\).

\paragraph{MST path for single linkage.} The single-linkage dendrogram is the MST of the complete graph~\cite{gower1969minimum}. By computing the MST of each component's \emph{sparse} sub-graph, we obtain the exact single-linkage dendrogram in \(\Onotation{m_k \log m_k}\) time and \(\Onotation{n_k + m_k}\) memory per component~--- no dense sub-matrix is ever formed. The MST has exactly \(n - 1\) edges; GSHAC computes \(m = \Onotation{nk}\) edges, where \(k\) is the average neighborhood size. Reducing \(\hmax\) to the minimum required by the application directly minimizes ~\(k\) and, thus, the computational cost.

\section{Experimental design}
\label{sec:expdesign}

Implementation details the C-backed library stack, the two HAC code paths, CRS-aware distance dispatch, and the scikit-learn API are deferred to Appendix~\ref{sec:system} so as not to interrupt the path from theory to evaluation. The implementation is available at \url{https://github.com/mine-the-gap/gshac} under the GPL-3.0 license.

We evaluate GSHAC along three research questions:

\begin{description}[leftmargin=*,topsep=2pt,itemsep=1pt]
  \item[RQ1 (Exactness):] Does the system produce identical cluster assignments to the dense baseline across the supported linkage methods and configurations?
  \item[RQ2 (Scaling):] How does empirical time and memory scaling match the theoretical predictions of Section~\ref{sec:complexity}?
  \item[RQ3 (Practical limits):] At what scale does the system remain feasible on commodity hardware and real-world datasets?
\end{description}

\paragraph{Datasets.}
We use three datasets at increasing scale:

\begin{enumerate}
    \item \textbf{Synthetic.} Clustered point clouds from a Gaussian mixture model: \(C\) centers placed uniformly in a \(500 \times 500\)\,km projected domain, \(n\) points displaced by Gaussian noise~\(\sigma\). Three density scenarios vary \(C\) and~\(\sigma\) relative to~\(\hmax\): \textbf{tight} (\(C\!=\!100\), \(\sigma\!=\!0.03\hmax\)) --- compact, well-separated clusters (best case); \textbf{moderate} (\(C\!=\!50\), \(\sigma\!=\!0.10\hmax\)); \textbf{loose} (\(C\!=\!20\), \(\sigma\!=\!0.30\hmax\)) --- broad, overlapping clusters (adversarial case). Figure~\ref{fig:scenarios} illustrates these scenarios. Sizes: \(n \in \{1{,}000,\ldots,50{,}000\}\), \(\hmax \in \{10, 20, 50\}\)\,km.

    \item \textbf{Standard 2-D clustering benchmarks.} Two moons and two circles (\(n = 500\) each)~\cite{pedregosa2011sklearn}, the canonical non-convex shapes used to test density-based clustering. We use them to visually illustrate that GSHAC produces partitions identical to dense single-linkage HAC.

    \item \textbf{GeoNames} (\(n = 2{,}000{,}000\)). Spatially stratified random sample (14.9\%) from the GeoNames \texttt{allCountries} database (\(n_{\text{full}} = 13{,}412{,}837\), CC~BY~4.0)~\cite{geonames2025}, using \(1^{\circ}\!\times\!1^{\circ}\) grid cells with proportional allocation. Haversine metric, \(\hmax \in \{1\,\text{km},\allowbreak\, 5\,\text{km},\allowbreak\, 10\,\text{km},\allowbreak\, 20\,\text{km}\}\), single linkage.
\end{enumerate}

\paragraph{Baselines and comparisons.} (i)~Dense baseline: complete \(\Onotation{n^2}\) matrix via \texttt{scipy\allowbreak .spatial\allowbreak .distance\allowbreak .cdist} for Euclidean (or a manual nested loop for haversine, since \texttt{cdist} lacks a haversine kernel) followed by \texttt{fastcluster.\allowbreak linkage} \cite{mullner2013fastcluster}, the fastest available dense HAC implementation for Python. The dense haversine baseline for the GeoNames dataset is reported analytically because the corresponding matrix exceeds available RAM. (ii)~scikit-learn \texttt{AgglomerativeClustering} with sparse \texttt{connectiv \allowbreak ity}~\cite{pedregosa2011sklearn} (single linkage only;\footnote{scikit-learn carries a documented bug (issue \#23550~\cite{sklearn_issue23550}) causing incorrect results for complete/average linkage with \texttt{distance\_threshold} and sparse connectivity.}). (iii)~PySAL \texttt{DistanceBand}~\cite{rey2007pysal} (graph construction only). (iv)~\texttt{sklearn.cluster.HDBSCAN} v1.8~\cite{mcinnes2017hdbscan} (scope comparison; non-equivalent outputs).

\paragraph{Metrics and hardware.} Wall time (seconds) and peak memory (binary units, MiB/GiB) via \texttt{tracemalloc}, averaged over \(r = 5\) repetitions; peak memory is reported separately for the graph-construction phase, the HAC phase, and the whole pipeline. Every timed measurement of the synthetic, constant-\(\bar{k}\), and GeoNames benchmarks---each dense run and each sparse run, at every repetition---executes in its own fresh subprocess. For GeoNames this reclaims memory between runs; for the dense-vs-sparse comparisons it additionally ensures each measurement is \emph{cold}, and that the dense baseline and the sparse pipeline pay the full fresh-process cost symmetrically. The dense baseline allocates a new \(\Onotation{n^2}\) distance matrix on every invocation, and in a long-lived benchmark process the memory allocator amortises the associated allocation and first-touch page-fault cost across repetitions, understating the wall time a practitioner pays when clustering a dataset \emph{once}; measuring each repetition in a fresh process reports that realistic one-shot cost. That one-shot cost itself depends on how the operating system backs the \(\Onotation{n^2}\) allocation: NumPy requests transparent huge pages for large arrays, and whether the kernel can grant them varies with memory fragmentation at run time, making the first-touch page-fault cost bimodal (on our hardware the cold dense baseline at \(n = 25{,}000\) takes \({\sim}3.5\)\,s when backed by 2\,MiB huge pages versus \({\sim}7.6\)\,s with 4\,KiB pages). The harness therefore disables the huge-page request (\texttt{NUMPY\_MADVISE\_HUGEPAGE=0}), pinning every measurement to the deterministic 4\,KiB-page state. Pinning to 4\,KiB pages rather than to huge pages is the only reproducible choice---huge pages can be requested but not enforced from user space, since whether the kernel grants them depends on fragmentation beyond the harness's control---and it is also the state a long-running analysis machine converges to as its memory fragments, so the pinned measurements are representative of practice; the setting applies to both methods alike, though it materially affects only the dense baseline's \(\Onotation{n^2}\) allocation. On a system that does grant huge pages, the dense baseline runs up to \({\sim}2\times\) faster and the reported wall-time speedups shrink accordingly. For the dense-feasible configurations, exactness (ARI) is verified in a separate, untimed in-process pass so it never perturbs a timed region; every timed repetition additionally records a fingerprint of its partition (computed after measurement stops), so repetition-level identity is itself measured. The PySAL graph build and the exactness illustration are deterministic single runs, and the scikit-learn end-to-end comparison is timed in-process with both sides measured identically. Correctness: Adjusted Rand Index (ARI) and cluster-count agreement at each cut height. All experiments on an AMD Ryzen~7 PRO 8840U laptop (8 cores, 3.3--5.1\,GHz), 30\,GiB DDR5, Ubuntu Linux (kernel 6.17, Python 3.12.3). Both GSHAC and the dense baseline execute single-threaded---none of the timed kernels (\texttt{cKDTree}, \texttt{BallTree}, \texttt{fastcluster}, the C extension) is multithreaded, and the harness pins all BLAS/OpenMP thread pools to one thread---so all reported speedups are a like-for-like single-core comparison.

\section{Results}
\label{sec:results}

This section reports experimental results across three research questions. Section~\ref{sec:correctness} validates exactness against a dense baseline. Section~\ref{sec:scaling} characterises scaling behaviour under fixed-domain and constant-$\bar{k}$ regimes. Section~\ref{sec:realworld} demonstrates feasibility on real-world datasets at scales where dense HAC is analytically infeasible. All experiments were conducted on a 30\,GiB workstation unless otherwise stated.

\subsection{Correctness (RQ1)}

For all 36 configurations where the dense baseline was feasible (\(n \leq 25{,}000\); 3~scenarios \(\times\) 4~sizes \(\times\) 3~\(\hmax\) values), GSHAC (single linkage) reproduced the dense baseline's partition exactly at every cut height---identical cluster assignments, adjusted Rand index (ARI)~=~1.0---across all five repetitions, confirming Theorem~\ref{thm:exact}: each timed repetition fingerprints its partition (a hash of its label vectors, computed after measurement stops) inside its own subprocess, the fingerprints agree across all repetitions of every configuration, and a separate untimed pass certifies the common partition against the dense baseline. For the 9 sparse-only configurations at \(n = 50{,}000\), the per-repetition fingerprints likewise agree, and two additional independent runs on identical input produce byte-identical cluster assignments, verifying deterministic reproducibility. We additionally verified the multi-linkage guarantee directly: on 48 dense-feasible configurations spanning single, complete, average, and Ward linkage, GSHAC reproduced the dense \texttt{fastcluster} partition exactly (ARI~=~1.0) at every cut~--- confirming Theorem~\ref{thm:exact} for single, complete, and average linkage, and matching dense Ward in every tested case (cf.\ the Ward remark in Section~\ref{sec:correctness}).

Figure~\ref{fig:exactness} illustrates exactness on two standard non-convex benchmarks, two moons and two circles (\(n = 500\) each). With \(\hmax = 0.20\), GSHAC computes only 5.3\% of the pairwise distances for two moons (6{,}617 of 124{,}750 pairs) and 4.3\% for two circles (5{,}329 of 124{,}750), decomposing each shape into 2~connected components. At every tested cut height \(h \leq \hmax\) the GSHAC partition is identical to that of dense \texttt{fastcluster} (ARI~=~1.0): for two moons, from 7~clusters at \(h = 0.10\) down to the 2~true clusters at \(h = 0.20\); for two circles, from 11~clusters at \(h = 0.10\) down to 2. Single linkage recovers the non-convex shapes exactly while computing only a small fraction of the distances.

Although GSHAC and \texttt{fastcluster} may traverse tied distances in different internal orders---GSHAC extracts a minimum spanning tree from the sparse graph and merges via union-find, whereas \texttt{fastcluster} processes the full condensed distance vector with a nearest-neighbour-chain algorithm---the resulting partition at any cut \(h \leq \hmax\) is invariant to merge order: it is uniquely determined by the set of pairwise distances below the threshold. This is exactly the guarantee of Theorem~\ref{thm:exact}, and is why the GSHAC and dense columns of Figure~\ref{fig:exactness} are identical despite different internal merge sequences.

\subsection{Scaling behavior (RQ2)}
\label{sec:scaling}

All scaling experiments in this section use \emph{single} linkage. We verified that GSHAC also reproduces the dense baseline exactly for complete, average, and Ward linkage (Section~\ref{sec:correctness}), but only single linkage uses the MST path that keeps per-component memory linear in component size; the other linkages materialise the per-component dense sub-matrix and therefore do not scale to the largest datasets (Section~\ref{sec:discussion}). The results below characterise the single-linkage profile.

Figure~\ref{fig:scaling} shows wall time and peak memory as a function of~\(n\) for both approaches across the three scenarios at three~\(\hmax\) values. In this fixed-domain setup, point density increases with~\(n\) and \(\bar{k}\) grows proportionally, so both approaches exhibit quadratic scaling (see Section~\ref{sec:constk} for the constant-\(k\) regime). The crossover occurs between \(n = 1{,}000\) and \(n = 5{,}000\) for the tight and moderate scenarios at \(\hmax \in \{10, 20\}\)\,km; at \(\hmax = 50\)\,km the sparse graph is dense enough that the wall-time advantage largely erodes---to \(1.10\times\) (tight) and \(0.91\times\) (moderate) at \(n = 25{,}000\), reversing to \(0.50\times\) in the loose scenario---while the memory advantage persists in every configuration. For \(n \geq 50{,}000\) the dense baseline exceeds available memory and is omitted; GSHAC continues to scale.

At \(n = 25{,}000\) (the largest dense-feasible size on our hardware), the maximum time speedup is \(\mathbf{5.56\times}\) (tight, \(\hmax = 10\)\,km) and the maximum memory reduction is \(\mathbf{20.2\times}\) (tight, \(\hmax = 10\)\,km). Even at \(n = 25{,}000\) in the adversarial case (loose, \(\hmax = 50\)\,km, \(\bar{k} \approx 1{,}775\)) GSHAC achieves \(3.25\times\) memory reduction despite being \(0.50\times\) slower in wall time~--- reflecting the high graph density in this worst-case scenario where the sparse graph approaches the complete graph. For \(n \geq 50{,}000\) no dense comparison is possible as the condensed distance matrix alone reaches \(\approx\!9.3\)\,GiB (the full \(n \times n\) matrix is twice as large, \(\approx\!18.6\)\,GiB); we quote the condensed size for these dense-infeasibility figures throughout, as it is what an optimised dense HAC actually allocates.

This split matters for generality: the sparse distance graph is a reusable output valid for other algorithms (spectral clustering, MST computation, network analysis).

\subsubsection{Constant-\texorpdfstring{$k$}{k} Scaling}
\label{sec:constk}

The fixed-domain benchmarks above increase~\(n\) while holding the spatial domain constant, causing point density (and hence the mean neighbourhood size~\(\bar{k}\)) to grow proportionally to~\(n\). Under this regime, the sparse graph has \(\Onotation{n\bar{k}} = \Onotation{n^2}\) edges, so both GSHAC and the dense baseline scale quadratically (Figure~\ref{fig:scaling}).

This is \emph{not} the typical real-world scaling scenario. In practice, larger datasets cover larger geographic areas (national \(\to\) continental \(\to\) global inventories) while point density and the application-specific threshold~\(\hmax\) remain similar. Under this regime, \(\bar{k}\) stays bounded and the \(\Onotation{n\bar{k}\log n}\) time and \(\Onotation{n\bar{k}}\) memory complexity of GSHAC become near-linear.

To demonstrate this, we run a separate experiment with uniformly distributed points where the domain grows as \(L \propto \sqrt{n}\), holding the mean neighbourhood size \(\bar{k}\) constant across \(n \in \{1\text{K},\ldots,500\text{K}\}\). The choice of a single representative \(\bar{k}\) is consequential because it sets the absolute level of the measured curves; to establish that the scaling \emph{slopes} are determined by the algorithm itself rather than by this choice, we sweep \(\bar{k}_{\text{target}} \in \{20, 50, 126, 200\}\) and verify that the resulting curves are near-parallel on a log-log plot, confirming slope-invariance (Figure~\ref{fig:constk}). We report headline numbers for the primary configuration \(\bar{k}_{\text{target}} = 126\), which matches the empirical mean neighbourhood size of GeoNames-2M at \(\hmax = 20\)\,km (Table~\ref{tab:constk}). The primary curve confirms the theoretical prediction:
\begin{itemize}[nosep]
  \item \textbf{Memory scales linearly}: 5\,MiB at \(n\!=\!1\text{K}\)
    to 3.0\,GiB at \(n\!=\!500\text{K}\) (slope~\(\approx 1.0\) on
    log-log; same slope at every \(\bar{k}\) tested).
  \item \textbf{Time scales near-linearly}: 0.02\,s to 20\,s
    (log-log slope 1.14 at the primary \(\bar{k}\!=\!126\); 1.07--1.15
    across the four \(\bar{k}\) values).
  \item \textbf{Speedup grows with~\(n\) and is larger at lower density}:
    at \(n\!=\!25\text{K}\), GSHAC is 10.8 times faster and
    47 times more memory-efficient than fastcluster at
    \(\bar{k}\!=\!126\); at \(\bar{k}\!=\!50\) the same ratios reach
    27 times and 118 times.
  \item At \(n\!=\!500\text{K}\) and \(\bar{k}\!=\!126\), GSHAC uses
    3.0\,GiB; the condensed distance matrix alone would require
    \(\approx\!0.9\,\text{TiB}\).
\end{itemize}

This experiment isolates the algorithmic scaling advantage from the artefact of increasing~\(\bar{k}\) in a fixed domain. The slopes are near-invariant across the \(\bar{k}\) sweep (Figure~\ref{fig:constk}), confirming that the asymptotic exponents are properties of the algorithm rather than of the chosen density: \(\bar{k}_{\text{target}}\) sets where the curves sit vertically, with only a small residual drift in slope (1.07 to 1.15 in time, 1.01 to 1.03 in memory across the tenfold span in \(\bar{k}_{\text{target}}\)). We attribute this drift to cache and memory-hierarchy effects (larger per-component sparse-matrix and MST buffers at higher \(\bar{k}\) incur more cache misses) that the Big-O analysis abstracts away; the drift is bounded and does not alter the linear-in-\(n\) scaling claim for fixed \(\bar{k}\). The result aligns with the GeoNames benchmark, whose empirical \(\bar{k}\) values fall within the swept range (from \(\approx\!1\) at \(\hmax\!=\!1\)\,km up to 126 at \(\hmax\!=\!20\)\,km), bounded by the spatial distribution of the data.

\subsubsection{Graph construction efficiency}

Table~\ref{tab:pysal} compares graph construction time against PySAL's \texttt{DistanceBand}. GSHAC uses \texttt{cKDTre \allowbreak e.query\_pairs}, a pure-C routine returning an array, whereas \texttt{DistanceBand} calls \texttt{cKDTree.sparse\_distance\_matrix} to build a Python dictionary-of-keys object. The result is a \textbf{13--81} times speedup across all tested scenarios and sizes, with the advantage growing with~\(n\).

\subsection{Real-world datasets (RQ3)}
\label{sec:realworld}

To evaluate GSHAC at scale on open, reproducible data, we apply it to a 2-million-point spatially stratified sample of GeoNames. We first establish feasibility across a range of distance thresholds where the dense baseline is analytically impossible (Section~\ref{sec:geonames}), then characterise scaling in the two regimes that bracket real-world data growth (Section~\ref{sec:geoscaling}), and finally contrast resource profiles against the most common density-based alternative, HDBSCAN (Section~\ref{sec:hdbscan}).


\subsubsection{GeoNames feasibility}
\label{sec:geonames}

Table~\ref{tab:geonames} summarises results for the 2M-point GeoNames sample across four distance thresholds. All four are feasible on the same 30\,GiB workstation, with total runtimes between 1.5 and 2.3\,minutes. The sparse graph stores at most 1.9\,GiB (at \(\hmax = 20\)\,km)~--- an \(8{,}000\)--\(16{,}000\) times reduction relative to the dense distance matrix (\(\approx\!15\)\,TiB in condensed form, the representation an optimised dense HAC requires; \(\approx\!29\)\,TiB as a full square matrix).

The MST path's role is most visible at the larger thresholds. The largest connected component grows from 88{,}624 features at \(\hmax = 5\)\,km (a 58.5\,GiB hypothetical dense sub-matrix) to 397{,}264 at \(\hmax = 10\)\,km (1.15\,TiB) and to 1{,}035{,}840 at \(\hmax = 20\)\,km --- over half of the sampled features in a single component, with a 7.8\,TiB dense sub-matrix. The MST-based single-linkage path never materialises any of these: peak HAC memory stays at \textbf{438\,MiB}, \textbf{1.1\,GiB}, and \textbf{5.7\,GiB} respectively (\({\sim}137\), \({\sim}1100\), and \({\sim}1410\) times reductions over the dense alternative). The contrast between Table~\ref{tab:geonames}'s analytical \emph{Max sub-matrix} row and the measured \emph{Peak memory (HAC)} row is the central technical reason GSHAC remains feasible as components grow large: under single linkage the MST path turns per-component HAC memory from \(\Onotation{c_k^2}\) into \(\Onotation{n_k + m_k}\).

\input{./tab_geonames.tex}

Runtime is non-monotonic in \(\hmax\). The non-singleton component count falls as components consolidate (201\,K \(\to\) 148\,K \(\to\) 48\,K \(\to\) 11\,K at 1\,/\,5\,/\,10\,/\,20\,km), and HAC time---driven by per-component overhead (sub-matrix extraction, MST, union-find)---tracks this count rather than the edge count (93\,/\,105\,/\,47\,/\,61\,s). Graph construction, in contrast, grows monotonically with edge count (28\,/\,33\,/\,44\,/\,74\,s), giving total times of \(2.0\,/\,2.3\,/\,1.5\,/\,2.2\)\,min. The 10\,km threshold is fastest overall; at 20\,km the 125.8\,M-edge graph becomes the dominant cost, marking the binding-constraint shift from HAC to graph construction that the complexity analysis predicts.


\subsubsection{Scaling on real geographic data}
\label{sec:geoscaling}

Section~\ref{sec:constk} established near-linear scaling on synthetic data at constant \(\bar{k}\). We now confirm it on real geographic data and contrast it with the adversarial regime, using the same 2M GeoNames sample at \(\hmax = 10\)\,km grown two different ways (Figure~\ref{fig:geoscaling}).

\paragraph{Constant density --- the realistic regime.} Real inventories grow by covering \emph{more area} at similar density (national \(\to\) continental \(\to\) global). We emulate this by taking geographic windows of the sample---a widening longitude strip---so the local sampling rate, and hence \(\bar{k}\), stays bounded (\(\bar{k}\) between 38 and 54 as \(n\) grows from 100\,K to 2\,M). In this regime GSHAC scales \textbf{near-linearly}: time as \(n^{1.14}\) and memory as \(n^{0.98}\), clustering the full 2\,M points in \textbf{91\,s} using \textbf{6.9\,GiB}. This is the headline scalability result, and it matches how spatial datasets actually grow.

\paragraph{Growing density --- the adversarial limit.} If instead \(n\) is increased by subsampling more densely within a \emph{fixed} extent, density and therefore \(\bar{k}\) grow in proportion to \(n\) (\(\bar{k}\) from 1.9 at 100\,K to 37.8 at 2\,M). The graph then stops being sparse: the edge count grows as \(\Onotation{n^2}\) and memory converges toward the quadratic behaviour of a dense method (measured slope \(n^{1.71}\), asymptoting to \(n^2\); time stays \(\sim\!n^{1.0}\) because graph construction dominates). This is the worst case for GSHAC. \textbf{Crucially, GSHAC remains feasible even here}: at \(n = 2\)\,M it still completes in 6.9\,GiB on the 30\,GiB workstation, whereas the dense matrix (\(\approx\!29\)\,TiB) and even its condensed form (\(\approx\!15\)\,TiB) are orders of magnitude beyond any workstation's memory. The distance threshold bounds what is ever stored, so feasibility holds in \emph{both} regimes---GSHAC degrades gracefully from near-linear toward quadratic as density grows, rather than failing outright. Graph-construction wall time at a given \(n\) additionally depends on the memory locality of the input ordering (the GeoNames experiments traverse the sample in different orders), so absolute times should be compared within, not across, experiments; memory and scaling exponents are unaffected.

\subsubsection{Scope Comparison}
\label{sec:hdbscan}

HDBSCAN~\cite{mcinnes2017hdbscan} is the most widely used density-based clustering algorithm for large spatial datasets, and practitioners commonly use it as a substitute for exact HAC. Therefore, for scope comparison, we present the resource profiles of HDBSCAN and our GSHAC. This is not a benchmark between equivalent algorithms, as they solve different problems and produce non-interchangeable outputs. Our illustrations show resource profiles using a single implementation (\texttt{sklearn.cluster.\allowbreak HDBSCAN} v1.8).

HDBSCAN constructs a mutual-reachability MST to produce a density-based cluster tree. Its clusters reflect density, not distance thresholds; 12.7\% to 35.2\% of features may be labeled as noise (depending on \texttt{min\_cluster\_size}); and results depend on \texttt{min\_cluster\_size} rather than a geographic distance parameter. Neither complete, average, nor Ward linkage is available.

Table~\ref{tab:hdbscan} reports timing, memory, and cluster counts on a 100\,K subset of the GeoNames sample (haversine, \(\hmax = 10\)\,km), measured for both methods within one harness. GSHAC completes in \textbf{5.6\,s}~--- \textbf{39--41 times faster} than either HDBSCAN run (229\,s at \texttt{mcs}\,=\,2, 219\,s at \texttt{mcs}\,=\,5) at comparable peak memory. HDBSCAN's runtime is essentially independent of \texttt{min\_cluster\_size} (229\,s vs.\ 219\,s), so no setting makes it time-competitive. The gap widens with scale: \texttt{sklearn}'s HDBSCAN scales super-linearly on haversine input (scaling probe over \(n \in \{10\text{K},\ldots,100\text{K}\}\): log-log slope~\(\approx 1.9\)), so it extrapolates to \(\approx\!18\,\text{h}\) on the full 2M sample, versus GSHAC's minutes (Section~\ref{sec:geonames}).

HDBSCAN assigns 12.7\% (\texttt{mcs}\,=\,2) to 35.2\% (\texttt{mcs}\,=\,5) of features as noise, whereas GSHAC assigns every feature to a cluster. GSHAC's counts follow from one interpretable parameter, the cut height~\(h\): a single 5.6\,s run produces a full dendrogram cuttable at any \(h \le \hmax\) (e.g.\ 56{,}141 clusters at 10\,km, 80{,}571 at 5\,km), whereas HDBSCAN requires a separate run per \texttt{min\_cluster\_size} and cannot produce standard linkage dendrograms.

\section{Discussion}
\label{sec:discussion}

The system is beneficial whenever the analyst has a meaningful upper bound~\(\hmax\) on the clustering distance, which arises naturally in environmental, regulatory, and operational contexts. The speedup grows with \(n/k\): tight clustering relative to~\(\hmax\) yields the largest gains. Two scenarios yield little benefit. \emph{First}, when \(\hmax\) approaches the dataset's spatial extent, the graph approaches the complete graph and \(k \approx n\). \emph{Second}, even with small overall~\(k\), a single very large component can dominate runtime for non-single linkages: at \(\hmax = 5\)\,km GeoNames already contains an 88{,}624-feature component, whose dense sub-matrix (58.5\,GiB) exceeds a 30\,GiB workstation for complete/average/Ward. The MST path eliminates this bottleneck for single linkage. The \(\Onotation{n \log n}\) overhead of spatial indexing exceeds the negligible setup cost of the dense baseline at very small~\(n\) (\(n < 200\) in our experiments); the system targets moderate to large~\(n\).

The component size distribution is the key determinant of performance. In GeoNames most components are small---at \(\hmax = 1\)\,km the median component size is~1 and the 99th percentile is~5---so the system processes them in microseconds. The largest component, however, reaches 88{,}624 features at \(\hmax = 5\)\,km, 397{,}264 at \(\hmax = 10\)\,km, and 1{,}035{,}840 at \(\hmax = 20\)\,km, corresponding to dense sub-matrices of 58.5\,GiB, 1.15\,TiB, and 7.8\,TiB respectively (Table~\ref{tab:geonames}) that no commodity workstation could materialise, yet the MST single-linkage path handles them in 438\,MiB, 1.1\,GiB, and 5.7\,GiB. This robustness comes from the MST path's complexity: it constrains HAC memory growth from quadratic to linear in component size, keeping the system feasible as components consolidate at larger \(\hmax\).

Theorem~\ref{thm:exact} covers single, complete, and average linkage (with Ward exact in practice for spatially compact clusters; Section~\ref{sec:correctness}), but practical performance varies. Single linkage benefits most from the MST path (\(\Onotation{n_k + m_k}\) memory per component, no dense sub-matrix). Complete, average, and Ward instead materialise the dense sub-matrix per component, so feasibility depends on the largest component fitting in RAM: at GeoNames \(\hmax = 5\)\,km (88,624-feature largest component, 58.5\,GiB) only single linkage is practical, and at \(\hmax \ge 10\)\,km the dense sub-matrix (\(\ge\!1\)\,TiB) rules out the other linkages entirely. The reported time and memory are therefore the single-linkage profile; complete, average, and Ward share a heavier profile dominated by the \(\Onotation{\max_k c_k^2}\) term.

Section~\ref{sec:hdbscan} shows that \texttt{sklearn} HDBSCAN is 39--41 times slower on a 100\,K GeoNames subset, a gap that widens with scale (HDBSCAN scales super-linearly, \(\sim\!n^{1.9}\)). The deeper issue is semantic: HDBSCAN clusters reflect density, not distance thresholds. In applications where ``all features within \(h\)\,km constitute one site'' is a regulatory or operational definition, density-based alternatives are not substitutes. 
%\texttt{genieclust}~\cite{gagolewski2021genieclust} modifies the merge order for robustness, producing non-standard dendrograms, which are also .

In the sparse-input exact HAC framework (parallels work in bioinformatics~\cite{loewenstein2008efficient,nguyen2014sparsehc}), BLAST-threshold similarity graphs serve the same structural role as the geographic distance graph. The geographic setting offers a practical advantage: metric distances enable efficient graph construction in \(\Onotation{n \log n + m}\) via spatial indexes, whereas bioinformatics methods require external pre-computation (e.g., all-against-all BLAST).

In the loose synthetic scenario at \(\hmax = 50\)\,km, GSHAC is slower than fastcluster in wall time (speedups of \(0.5\)--\(0.95\times\) across sizes, worst at \(n = 25{,}000\)). This reflects the high graph density in this adversarial regime (up to \(\bar{k} \approx 1{,}775\), graph density 7\%, at \(\hmax = 50\)\,km): the sparse representation carries overhead (index lookups, sparse matrix operations) that a contiguous condensed array avoids. A full native implementation of the sparse-matrix extraction and component loop would further reduce this gap.

Crucially, the \emph{memory} advantage is structural: GSHAC stores \(\Onotation{n \bar{k}}\) entries versus \(\Onotation{n^2}\), yielding 3.3--20 times lower peak memory across all scenarios. At \(n \geq 50{,}000\), the dense baseline is infeasible regardless of implementation: the condensed matrix alone reaches \(\approx\!9.3\)\,GiB. The asymptotic time complexity \(\Onotation{n \bar{k} \log n}\) versus \(\Onotation{n^2}\) guarantees that GSHAC will outperform any dense implementation beyond a dataset-dependent crossover.

Müllner~\cite{mullner2013fastcluster} benchmarked \texttt{fastcluster} against \texttt{scipy.cluster \allowbreak .hierarchy}, R's \texttt{hclust}, MATLAB, and Mathematica on synthetic Gaussian-mixture data up to \(n \approx 20{,}000\), demonstrating that optimal algorithm selection (MST-based single linkage, nearest-neighbor chain for complete/average/Ward) reduces the HAC step from \(\Onotation{n^3}\) to \(\Onotation{n^2}\). These experiments assume the condensed distance matrix is already in memory and therefore do not measure the dominant cost for large geospatial datasets: computing and storing \(\binom{n}{2}\) distances. For the 2M GeoNames sample, this condensed matrix alone would require \(\approx 15\)\,TiB~--- three orders of magnitude beyond workstation RAM~--- so \texttt{fastcluster} cannot even be invoked. GSHAC is complementary rather than competitive: it eliminates the \(\Onotation{n^2}\) storage bottleneck that Müllner explicitly identifies but does not address, then delegates per-component HAC to a fastcluster-style \(\Onotation{c_k^2}\) routine operating on dense sub-matrices that fit in memory. In the constant-\(\bar{k}\) regime where \(\bar{k}\) is bounded by data locality (the typical case for geographic data; empirical \(\bar{k}\) values in our experiments span roughly 1--130, and slope-invariance was verified across \(\bar{k}_{\text{target}} \in \{20, 50, 126, 200\}\)), this reduces the end-to-end complexity from \(\Onotation{n^2}\) to \(\Onotation{n \log n}\), enabling datasets two to three orders of magnitude larger on identical hardware (Table~\ref{tab:constk}, Figure~\ref{fig:constk}).

The algorithm requires only a spatial range query capability and an exact pairwise distance function. Beyond point coordinates, the implementation therefore also supports line, polygon, and mixed-geometry inputs in projected CRSs: a GEOS STRtree \texttt{dwithin} range query replaces the KD-tree/Ball-tree, and exact boundary-to-boundary minimum distances---0 for touching or overlapping features, following the GEOS/\texttt{sf}/PostGIS convention---replace the point kernels. The component-decomposition core and the exactness guarantee are unchanged, since Theorem~\ref{thm:exact} requires only a complete enumeration of pairs within \(\hmax\) with exact dissimilarities; only the range query and distance kernel differ, at a higher per-pair kernel cost than for points. Ward linkage is refused for non-point features because its merge criterion requires a Euclidean embedding that set distances do not provide. All experiments in this paper use point features. Geodesic boundary-to-boundary distances for geographic-CRS geometries remain future work; recent TSAS work on secondary-partitioning indexes for distance queries on non-point data~\cite{michalopoulos2025distance} demonstrates that polygon-aware range queries scale to large datasets, providing the indexing primitive for that extension. Non-metric dissimilarities that increase with geographic separation (e.g., travel time) are similarly tractable provided a spatial index over the alternative metric is available.

GSHAC's performance-critical paths (union-find linkage construction, batch dendrogram cutting, and haversine distance computation) are implemented as a C extension (\texttt{\_gshac.so}) with GIL release, following the same pattern as \texttt{fastcluster}~\cite{mullner2013fastcluster}. Graph construction and MST extraction use \texttt{scipy.spatial.cKDTree} and \texttt{scipy.sparse.csgraph}, both implemented in~C. The remaining Python orchestration (component decomposition, label assembly) accounts for a small fraction of total runtime.

Figure~\ref{fig:limits} projects the constant-\(\bar{k}\) scaling behaviour to larger datasets. The dense baseline becomes memory-infeasible beyond \(n \approx 50{,}000\) on a 30\,GiB workstation; GSHAC scales as \(\sim\!n^{1.1}\) in time and linearly in memory, remaining feasible into the millions as confirmed by the GeoNames (\(n = 2\text{M}\)) benchmark and the constant-density geographic experiment (Section~\ref{sec:geoscaling}). The component-wise architecture is embarrassingly parallel: each component's HAC can run independently. GeoNames at \(\hmax = 10\)\,km decomposes into 114{,}716~components; with the laptop's 8~cores, a na\"ive parallel map could reduce the HAC phase substantially. We have not explored this direction, but note that GSHAC's low per-component memory footprint makes multi-core execution practical even on commodity hardware. Because the dense nearest-neighbour-chain linkage is inherently sequential and admits no comparable component decomposition, the single-core speedups reported in Section~\ref{sec:scaling} are conservative with respect to GSHAC's achievable parallel throughput. Absolute wall-clock speedups nonetheless remain system-dependent---they vary with the CPU frequency governor and with memory-allocation and paging behaviour (in particular transparent-huge-page availability; Section~\ref{sec:expdesign})---and should be read as representative rather than exact; the memory-reduction factors, log-log scaling exponents, and exactness are hardware-independent and constitute the reproducible core results.

\section{Conclusion}
\label{sec:conclusion}

We presented a system for scalable exact hierarchical clustering of spatial data that replaces the \(\Onotation{n^2}\) dense distance matrix with an \(\Onotation{nk}\) sparse geographic distance graph built via spatial indexing. We proved exactness for single, complete, and average linkage (with Ward exact in practice for spatially compact clusters), and provided a \texttt{SparseAgglomerativeClustering} estimator with a scikit-learn-compatible API. On a 2M-point GeoNames sample, four thresholds from 1 to 20\,km each complete in under 2.5\,minutes within 22\,GiB on a single 30\,GiB workstation, where the dense matrix (\(\approx\!29\)\,TiB) is infeasible; under constant density the method scales near-linearly to millions of points. To our knowledge, these are the largest demonstrations of exact geographic HAC on a single workstation.

Future work includes: (i)~adapting the system for streaming settings where features arrive incrementally; (ii)~extending to parallel execution for datasets beyond single-machine memory; (iii)~applying the sparse geographic graph as a general-purpose input to other distance-based spatial algorithms; and (iv)~developing memory-efficient HAC paths for complete, average, and Ward linkage analogous to the MST-based single-linkage optimisation.

\section{System architecture}
\label{sec:system}

The Python implementation is backed by C libraries for all computationally intensive operations:
\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=1pt]
  \item \texttt{scipy.spatial.cKDTree} \cite{virtanen2020} for Euclidean range queries;\\ \texttt{sklearn.\allowbreak neighbors.\allowbreak BallTree} \cite{pedregosa2011sklearn} with the haversine metric for geodesic range queries.
  \item \texttt{scipy.sparse.\allowbreak csr\_matrix} for the sparse distance graph.
  \item \texttt{scipy.sparse.\allowbreak csgraph.\allowbreak connected\_\allowbreak components} for component decomposition.
\end{itemize}

\subsection{Input formats and CRS-aware dispatch}

The implementation accepts input coordinates either as a raw \((n, 2)\) numeric array or as a \texttt{geopandas} \texttt{GeoSeries}/\texttt{GeoDataFrame}, with an optional explicit \texttt{crs=} argument for the array form. When CRS information is available, the system dispatches the distance metric automatically based on whether the CRS is geographic or projected, following the precedent of \texttt{sf::st\_distance} in R~\cite{pebesma2018sf}: ellipsoidal geodesic distance is the default for geographic CRS, computed via \texttt{pyproj.Geod.inv} on the WGS-84 ellipsoid; Euclidean distance is the default for projected CRS. The dispatch layer rejects metric/CRS combinations that would silently produce wrong results --- for instance, requesting \texttt{haversine} on projected coordinates, or \texttt{euclidean} on geographic coordinates, raises an error rather than evaluating distance on the wrong manifold.

The default for geographic CRS is the ellipsoid rather than the sphere --- a deliberate departure from the s2-based default of \texttt{sf}. The motivation is correctness by default: clustering output of GSHAC is typically consumed by downstream maps, area summaries, or further analytical pipelines in which ellipsoidal correctness is a property the caller will assume rather than verify, and the absolute distance error of a spherical approximation compounds through subsequent area, length, and adjacency computations. The cost of this default is a constant-factor overhead in the distance-kernel stage of \texttt{spatial\_dist\_graph}: empirically about 1.0\(\times\) the C haversine kernel in sparse-graph regimes (\(\bar{k} \lesssim 10\), where the BallTree neighbour query dominates) and rising to \(\approx\!2.7\)--\(3.3\times\) in dense regimes (\(\bar{k}\) in the hundreds or thousands, where the distance kernel itself dominates). The asymptotic complexity is unchanged in both --- both paths are \(\Onotation{n \cdot k}\) --- so the constant-factor overhead is the price of correctness-by-default in this regime, and end users who require maximum throughput can opt back into the sphere.

The spherical \emph{haversine} metric remains explicitly available as \texttt{metric="haversine"} and is the metric we use for the geographic benchmarks of Section~\ref{sec:results}. We make this choice for two reasons. First, none of the dense-HAC implementations we benchmark against --- \texttt{fastcluster}~\cite{mullner2013fastcluster}, \texttt{scipy.cluster.hierarchy}, and scikit-learn's \texttt{AgglomerativeClustering}~\cite{pedregosa2011sklearn} with sparse connectivity --- exposes a native ellipsoidal-distance kernel: a fair distance-kernel-for-distance-kernel comparison therefore requires both sides to use the same spherical formula on \((\text{lon}, \text{lat})\) inputs, which isolates the contribution of the sparse-graph algorithm from the contribution of the distance kernel. Second, haversine is the kernel used by prior versions of the GSHAC package and by the C extension \texttt{\_gshac.so}; using it here keeps the experimental numbers continuous with that prior work. The maximum distance error of haversine relative to the WGS-84 ellipsoid is bounded by \(\sim\!0.5\%\) (worst case near the poles for short east-west chords, an order of magnitude smaller at mid-latitudes), which is well below the precision relevant to clustering at the spatial thresholds we evaluate; on a representative clustered \((\text{lon}, \text{lat})\) dataset the resulting edge sets agree at \(100\%\) of haversine's edges with only \(\approx\!0.005\%\) additional boundary edges captured by the geodesic path, and the connected-component counts are identical.

Line, polygon, and mixed-geometry inputs are supported in projected CRSs via a GEOS-backed path: \texttt{shapely.\allowbreak STRtree} range queries with the \texttt{dwithin} predicate enumerate all pairs within \(\hmax\) by true boundary-to-boundary minimum distance, and per-component sub-matrices for complete and average linkage are recomputed with the same GEOS kernel. Ward is refused for non-point input, and geographic-CRS geometries raise an error with a reprojection hint (GEOS distances are planar). All benchmarks in this paper use point features.

\subsection{Two HAC paths}
\begin{sloppypar}
For \emph{single linkage}, the system computes \texttt{scipy.sparse.\allowbreak csgraph.\allowbreak minimum\_\allowbreak spanning\_tree} on each component's sparse sub-matrix, then constructs the linkage matrix~\(Z\) via a union-find pass over the \(n_k - 1\) MST edges. This path is \(\Onotation{m_k \log m_k}\) time and \(\Onotation{n_k + m_k}\) memory~--- \emph{no dense matrix is formed}, regardless of component size. The resulting \(Z\) matrix is a standard scipy linkage matrix, supporting \texttt{fcluster} at any cut height \(h \le \hmax\) and full dendrogram visualisation. For \emph{other linkage methods} (complete, average, Ward): the full per-component distance matrix is recomputed from the original coordinates with the graph's metric---recovering the intra-component distances beyond \(\hmax\) that the threshold graph omits, as Theorem~\ref{thm:exact} requires---then condensed via \texttt{scipy.spatial.\allowbreak distance.\allowbreak squareform} and passed to \texttt{fastcluster.\allowbreak linkage}~\cite{mullner2013fastcluster}, with \texttt{scipy.cluster.\allowbreak hierarchy.\allowbreak linkage} as a fallback when fastcluster is unavailable.
\end{sloppypar}

Only the orchestration layer (component iteration, label assignment) is pure Python; all spatial queries, matrix operations, and HAC computations are C-backed --- via scipy/sklearn libraries for spatial indexing and matrix operations, and via a dedicated C extension (\texttt{\_gshac.so}) that implements union-find linkage construction over MST edges, haversine distance computation, and batch threshold-based dendrogram cutting with GIL release. A pure-Python fallback is used when the C extension is not built.

\subsection{scikit-learn API}
\begin{sloppypar}
To support adoption in existing pipelines we provide two public functions. \texttt{geographic\_con\-nectivity} returns a binary sparse CSR matrix encoding the distance-band graph, compatible with scikit-learn's \texttt{connectivity} parameter and other graph-based spatial tools. \texttt{Sparse\-Agglo\-mera\-tive\-Clus\-tering} is a full estimator inheriting \texttt{Base\-Estimator} and \texttt{Cluster\-Mixin}, mirroring the \texttt{Agglomer\-ative\-Cluster\-ing} API: the user specifies \texttt{h\_max}, \texttt{distance\_thresh\-old}, \texttt{linkage}, and \texttt{metric}, then calls \texttt{fit(X)} to obtain \texttt{labels\_}, \texttt{n\_clusters\_}, and \texttt{n\_con\-nected\_com\-ponents\_}.
\end{sloppypar}
